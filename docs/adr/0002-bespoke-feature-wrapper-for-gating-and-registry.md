# Bespoke feature wrapper for gating, instead of ad hoc `Effect`/`By_Default` composition

`wp-type-extensions` gives generic building blocks (`Effect`, `By_Default`) for conditionally booting a `Feature`, but no concept of a stable identifier for one. Composing those primitives ad hoc per feature works, but leaves no registry of "what features exist and are they on."

WP SEO needs more than a boot-time conditional: issue #131 requires a recommended-features doc, a readonly admin display in v2.0, and a lockable toggle UI in v2.1 that can tell whether a feature is filter-locked. All three need an enumerable registry of features, keyed by a stable handle.

Decision: wrap every feature in a WP SEO-specific class that pairs a `$handle` with a filter check, and doubles as the registry entry consumed by the v2.0 readonly display, the v2.1 toggle UI, and the docs generator. This is more code than plain composition, but the registry is required regardless, so building it in from the start avoids bolting on introspection later.

Two filters gate each handle: `wp_seo_enable_feature( bool $enabled, string $handle )` (global gate) is checked first, then `wp_seo_enable_{$handle}( bool $enabled )` (per-feature override), which receives whatever the global filter left. The value both filters start from is the wrapper's default — `false` for a top-level feature, but `true` for one nested inside a group that carries its own handle, per [ADR 0003](0003-nested-handles-for-feature-groups.md). An environment-scoped third filter is deliberately skipped for now — add it only when a specific feature actually needs environment-conditional enablement, not speculatively.

The registry is populated by the wrapper registering *itself* on construction, rather than by walking the composed feature tree or by substituting a registry-aware container for `Group`. Walking the tree isn't possible: `wp-type-extensions`' `Group` is `final` with a private, ungettable `$features` array. A WP SEO-specific container in place of `Group` would work, but only captures subtrees actually composed through it — any future use of the plain `Group` (the obvious import, and the one that ships in the dependency) would silently vanish from the registry. Because [ADR 0003](0003-nested-handles-for-feature-groups.md) routes every handle through this one wrapper regardless of nesting depth, self-registration can't be bypassed the same way. The cost is static mutable state, which requires an explicit reset hook for test isolation.

A handle is interpolated into a filter name, so it is validated on construction: it must match `^[a-z0-9_]+$`, and the literal `feature` is reserved, since a feature claiming it would name its per-handle filter identically to the global gate. The two are called with different numbers of arguments, so a consumer using the documented global signature would fatal. A feature that fails validation, or whose handle is already taken, refuses to boot — running behavior the registry cannot report would undermine the admin display in [ADR 0004](0004-readonly-settings-page-in-v2-0.md).
